생성 워크플로우

원천과 배포 — 버전 관리
원천
design.md를 포함한 모든 규칙의 원천은 사내 git 원격 저장소 하나다. 개인이 파일을 복사해 각자 첨부하는 방식은 금지한다. 버전 분기가 생기는 즉시 시스템이 무너진다.
Claude Code
항상 저장소를 pull 받아 사용하므로 자연히 최신 버전이다.
claude.ai
개인 프로젝트가 아니라 팀 공유 프로젝트 1개만 운영한다. 프로젝트 지식은 GitHub 연동으로 dist/design-standalone.md에 연결해, 저장소가 갱신되면 함께 갱신된다. 연동이 불가한 환경이면 CI 빌드 후 담당자 1인이 지식을 갱신한다.
standalone
dist/design-standalone.md는 손으로 편집하지 않는다. CI가 main 브랜치에서 자동 빌드한다.
버전 스탬프
빌드 시 문서 머리에 버전 번호·날짜·커밋 해시를 자동 삽입하고, 생성된 목업 하단에도 사용 버전을 표기한다. 구버전 문서로 생성된 결과물을 즉시 식별할 수 있다.
경로 1 — Claude Code
대상
개발자·디자이너
절차
페이지 생성 요청 → 해당 제품 regulations/ 검토 (충돌·주의사항 발견 시 생성 전에 알림) → design.md + 해당 레시피 읽기 → playground에 페이지 생성 → 기계 검증(lint) → dev 서버 미리보기 → 스크린샷 셀프 리뷰. CLAUDE.md가 이 절차를 강제한다.
경로 2 — claude.ai
대상
기획/PM·비개발 직군
절차
팀 공유 claude.ai 프로젝트에서 대화로 요청하면 React 아티팩트로 미리보기. standalone 문서에는 규정 검토 지침과 아티팩트 제약 대응 지침이 포함된다. 결과가 채택되면 개발자·디자이너가 경로 1에서 정식 목업화한다.

design.md 구성 — AI 규칙서

전제
사람용 가이드라인이 아니라 AI에게 내리는 명령문 형태로 작성한다.
강제 규칙
색·간격·라운드·그림자는 시맨틱 토큰만 사용. 임의 값 금지 (#3B82F6, p-[13px] 등).
컴포넌트 카탈로그
컴포넌트마다 {언제 쓴다 / 언제 안 쓴다 / props / 예시 코드} 블록.
페이지 레시피 인덱스
요청 유형 → 레시피 매핑 표.
레이아웃 규칙
사이드바/헤더 셸, 그리드, 반응형 브레이크포인트.
금지 목록
그라데이션 남발, 카드 안의 카드, 임의 그림자 등 안티패턴.
레시피 형식 예
admin-list — 사이드바 셸 + 페이지 헤더(제목, 주요 액션 버튼) + 필터 툴바 + DataTable + 페이지네이션. 각 구역에 사용할 컴포넌트와 토큰을 명시.

토큰 파이프라인

원천
dstk/*.json — W3C DTCG 표준, core → semantic 참조 구조.
산출 1
CSS 변수 + Tailwind 프리셋 → playground/목업용.
산출 2
피그마 Variables (라이트/다크 모드 포함) → Figma MCP로 주입.
산출 3
design-standalone.md 내 토큰 표 → claude.ai용.

피그마 기록 파이프라인

1회 셋업
토큰 → 피그마 Variables 생성, 핵심 컴포넌트 → 피그마 컴포넌트 라이브러리 생성. Code Connect로 피그마 ↔ 코드 컴포넌트 매핑.
화면 기록
승인된 목업 → 라이브러리 컴포넌트 인스턴스 + Variables 바인딩으로 화면 조립. 하드코딩 값 없는 정식 산출물.
재동기화
토큰/컴포넌트 변경 시 피그마 Variables·라이브러리 재생성.
히스토리 기록
피그마 파일에 전용 "History" 페이지를 두고, 화면을 기록·갱신할 때마다 날짜, 요청 내용(프롬프트 요약), 변경 사항, 디자인 시스템 버전, 승인자 엔트리를 시간순으로 추가. 기록된 각 화면 옆에도 동일 메타를 담은 주석 카드를 붙인다.

범위 제외 (v1)

역방향 동기화
피그마 → 코드 방향은 하지 않는다.
npm 배포
프로덕션 패키지 배포는 하지 않는다. 목업·승인용 레퍼런스 구현까지만.
타 스택 구현
React 외 스택용 컴포넌트는 만들지 않는다. 토큰만 중립 제공.
전용 웹 툴
사내 전용 웹 툴은 만들지 않는다. claude.ai로 대체.

파이프라인

1 업로드
제품 스크린샷 또는 HTML 파일을 입력으로 올린다.
2 컴포넌트 추출
화면을 판독해 UI 컴포넌트를 추출하고 그룹으로 분류한다 → 03 컴포넌트 채택에 카드로 등재.
3 shadcn 매핑
추출된 각 컴포넌트를 shadcn 기본형과 매핑한다. 03 카드의 기본 상태가 shadcn 렌더, hover가 원본 컷, 칩이 매핑 결과다. 직접 대응이 없으면 shadcn: 없음으로 표기하고 커스텀 제작 대상으로 남긴다.
4 채택 판정
03 카드에서 컴포넌트별 채택 여부를 토글로 결정한다 — 채택된 것만이 DS 어휘다(유일한 게이트). shadcn 매핑분은 기본형 위에 값 조정·토큰을 얹고, 매핑 없는 것은 원본 재현으로 제작 완료된 뒤 같은 채택 절차를 밟는다. 결과는 approved.json으로 커밋되어 팀과 공유된다.
5 페이지 생성
저장소를 클론한 폴더에서 Claude Code 세션에 바로 채팅하면 된다 — CLAUDE.md 계약이 자동 적용되어, 시작 시 git pull로 최신 DS를 받고 채택 컴포넌트·365 토큰만으로 뼈대 페이지를 만들어 대화로 다듬는다(기본·빈·로딩·에러 4개 상태 포함). 결과물은 각자 로컬 보관 — 절차는 05 사용법 · 갤러리 참고.
6 365 브랜딩 적용 예정
생성된 페이지를 미리보기 패널에서 확인하고 [365 DS 적용]으로 타이포·컬러·라운드 등 365 토큰을 입힌다. [shadcn]/[DS 적용] 탭으로 전환 비교, 우측에 HTML 코드 블록과 복사 버튼. 선행 조건: 365 토큰 값 정의(상태 색 도입 범위 포함).

365 DS = 채택 어휘에 365 토큰을 얹은 모습. 03에서 채택된 컴포넌트만 여기 올라온다 — shadcn 매핑분은 기본형 위에 값 조정·토큰, 원본 재현 제작분은 재현 코드에 같은 토큰. 미채택분은 여기 없다(현황은 03 우측 레일, 제작 대기열은 05). 365 토큰 값은 아직 1차(네이비·각짐)만 정의된 상태다.

템플릿 — 레이아웃 프레임을 번호로 고르는 선례

레시피는 페이지 유형이 아니라 레이아웃 프레임이다. 세션이 애매한 레이아웃을 만나면 "어느 프레임의 본문인가, 단독 화면인가"를 이 목록의 번호로 물어본다 — 여기 카드와 모달 선택지의 번호는 항상 같다 (원천: recipes/ 목록 순서). 본문 내용은 요청자가 가져오는 스크린샷·와이어프레임이 결정한다.

1 관리 콘솔 프레임
상단바
메뉴
본문 — 요청한 화면이 들어가는 곳
메뉴(사이드바) + 상단바 + 본문 — 내부 화면 전부의 기본 프레임. 표준 요청 문장: "스샷을 관리 콘솔 본문에 넣어줘". 프레임에 안 담기면 단독 화면.

사용법 — 세션에서 바로 생성

1 클론 (최초 1회)
git clone github.com/younginsa/designsystemin.md — 저장소 읽기 권한과 본인 계정으로 로그인한 Claude Code만 있으면 된다. 토큰은 각자 좌석에서 쓴다.
2 폴더에서 실행
클론한 폴더에서 claude 실행. 규칙(CLAUDE.md)·채택 어휘(approved.json)·365 토큰(ds365.json)이 자동 적용되고, 세션이 시작할 때 git pull로 항상 최신 DS를 받는다.
3 채팅
화면 스크린샷·와이어프레임을 드래그하고 "관리 콘솔 본문에 넣어줘"처럼 말한다 (영역 이름: 메뉴·상단바·본문). 뼈대가 먼저 나오고, 채팅으로 그 자리에서 다듬는다(재생성 없음). 모든 화면은 기본·빈·로딩·에러 4개 상태를 포함한다.
결과물
본인 로컬 playground/app/generated/<이름>/에 남는다 — 커밋하지 않고 각자 팀에서 활용한다. 채택 목록 밖 컴포넌트가 필요하면 세션이 만들지 않고 자리표시 후 보고한다.
DS 요청
쓰다가 필요한 게 생기면 세션에 "DS 요청: ○○ 추가 필요"라고 말한다 — Jira DES 보드로 티켓이 올라가고(본인 계정, 최초 1회 API 토큰 설정 필요), 디자이너가 반영해 커밋하면 모두에게 자동 배포된다. 자리표시가 발생하면 세션이 먼저 올릴지 물어본다.
