처음부터 따라하기 — 빠른 시작

1 최초 세팅
터미널에서 git clone https://github.com/younginsa/designsystemin.md → 폴더에서 claude 실행 → "프로젝트 훅 신뢰" 물음에 승인. 이후로는 켤 때마다 최신 DS가 자동 적용된다.
2 페이지 만들기
Claude Code에게 요구사항을 채팅으로 전달한다. 스크린샷·와이어프레임 드래그, "메인 레이아웃 본문에 넣어줘" 같은 요청 모두 가능. 세션이 질문하면 맨 아래 한 줄 양식으로 답한다 (예: 1 a go).
3 미리보기
세션이 주는 로컬 URL에서 확인한다 (기본·빈·로딩·에러 토글). 파일이 필요하면 "HTML로 줘" — 설치 없이 열리는 정적 파일로 추출된다.
4 결과물
본인 로컬 playground/app/generated/에 생성된다.
5 디자이너에게 요청
새로운 구성요소가 나오면 세션이 먼저 "Jira에 DS 요청으로 올릴까요?"를 묻는다. 직접 올리려면 "DS 요청: ○○ 추가 필요" — DES 보드에 요청자=본인으로 접수된다. (최초 1회: id.atlassian.com에서 API 토큰 발급 → ~/.zshrc에 JIRA_EMAIL·JIRA_API_TOKEN 등록 → 터미널 재시작)

생성 워크플로우

원천과 배포 — 버전 관리
원천
design.md를 포함한 모든 규칙의 원천은 사내 git 원격 저장소 하나다. 개인이 파일을 복사해 각자 첨부하는 방식은 금지한다. 버전 분기가 생기는 즉시 시스템이 무너진다.
자동 최신화
세션을 켤 때마다 훅이 git pull을 실행한다 — 클론은 항상 최신이고, 사용자가 할 일은 없다.
버전 표시
세션 하단 배지 365 DS 최신 ✓ · 날짜판과 첫 응답 첫 줄의 [365 DS] 상태 인용으로, 어느 버전 DS로 작업 중인지 항상 보인다.
세션이 따르는 절차 — CLAUDE.md 계약
생성 전
해당 제품 regulations/ 검토 (충돌 발견 시 생성 전에 알림) → design.md + 채택 어휘(approved.json) + 365 토큰 로드 → 레이아웃 프레임 대조("어느 프레임의 본문인가, 단독인가" — 애매하면 생성 전에 질문).
생성
뼈대 우선, 단일 파일 진화 — 수정은 재생성 없이 해당 부분만. 채택 어휘 밖 요소는 만들지 않고 자리표시 + DS 요청 제안.
생성 후
self-check(임의 값 grep) → dev 서버 렌더 확인 → 미리보기 URL 안내. 무거운 빌드 검증은 하지 않는다 — "HTML로 줘" 요청 시에만 빌드.

품질 검증

3단 게이트
기계 검증
self-check — 임의 색·임의 값 grep 검사 (#hex, -[..] 금지). 생성 직후 자동 실행.
시각 검증
세션이 dev 서버 렌더를 직접 확인한 뒤 전달한다.
사람 확인
최종 게이트. 요청자가 미리보기로 보고, 고칠 부분은 채팅으로 그 자리에서 수정.
